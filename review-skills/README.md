# review-skills

这一组 skills 用于在 `harness-team` 流程中做变更前/变更后评审摘要与专项风险审查。

## 设计原则

- **先通用，后专项**：先用通用评审原则把风险分级，再用专项 skill 深入检查具体问题。
- **低侵入**：尽量保持现有 skill 的使用方式不变，只补充组织说明和公共约定。
- **可组合**：同一次 review 可以同时使用多个专项 skill。
- **事实化输出**：结论尽量落到文件、行号、风险类型和可验证事实。

## 适用关系


| skill                        | 适用场景                       | 备注                                       |
| ---------------------------- | -------------------------- | ---------------------------------------- |
| `common-review`              | 所有 review 的通用底座            | 先看这个，再进专项                                |
| `prepare-review`             | 在 review 或提 PR 前整理变更摘要     | 偏信息整理，不做深入风险判断                           |
| `spring-architecture-review` | Spring Boot 分层、依赖方向、业务逻辑归属 | 重点看 Controller / Service / Repository 边界 |
| `sql-risk-review`            | SQL、Mapper、批量更新、分页和索引风险    | 重点看数据安全与性能                               |


## 选择建议

### 1. 先不确定该用什么

先用 `common-review`，再决定要不要加专项 skill。

适合场景：

- 还没看变更内容，只想先建立通用评审基线
- 需要统一风险分级和输出风格
- 改动范围看起来不大，但还不确定是否涉及架构或 SQL

### 2. 只需要提炼变更摘要

使用 `prepare-review`。

适合场景：

- 提 PR 前先整理变更目标和影响面
- 让 reviewer 快速理解这次改动做了什么
- 需要列出已运行测试、已知风险和未解决问题

### 3. 需要检查 Spring 分层和职责边界

使用 `spring-architecture-review`。

适合场景：

- Controller / Service / Repository 之间的依赖关系要确认
- 想检查业务逻辑是否放错层
- 想确认是否存在跨层调用或 Web 对象渗透到业务层

### 4. 需要检查数据库写操作和查询风险

使用 `sql-risk-review`。

适合场景：

- 涉及 UPDATE / DELETE / 批量操作
- 涉及分页查询、排序稳定性、索引和全表扫描风险
- 需要评估是否会影响大量数据或查询性能

### 5. 同时涉及架构和 SQL

先用 `spring-architecture-review`，再用 `sql-risk-review`。

原因：

- 先确认职责和边界是否合理
- 再检查具体 SQL 实现是否安全

### 6. 只是不确定该怎么组合

默认顺序：

1. `common-review`
2. `prepare-review`
3. `spring-architecture-review`
4. `sql-risk-review`

## 通用评审原则

所有 review 默认都应先关注以下问题：

1. **安全性**：是否会引入数据破坏、越权、误删误改等风险。
2. **正确性**：变更是否符合预期行为，是否存在明显的逻辑缺陷。
3. **影响范围**：是否会波及多个模块、公共路径或历史数据。
4. **可维护性**：实现是否清晰，是否容易被后续改动误用。
5. **可验证性**：是否能通过测试、日志或可观察行为验证结果。

## 输出风格

- 保持简洁、事实化，避免空洞表扬。
- 优先标出严重问题和未解决问题。
- 尽量给出文件路径、行号、风险类型和建议动作。
